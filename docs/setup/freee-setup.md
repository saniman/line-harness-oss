# freee 連携セットアップ

当日現金払いの参加者へ領収書を自動発行・送信するために、freee と OAuth2 で連携する。
実装は `apps/worker/src/services/freee-oauth.ts` / `apps/worker/src/routes/freee.ts`。

> 未設定でもイベント申込フロー自体は動く（領収書の自動化だけが使えない）。

## 前提：freee には「receipts」が2つある（取り違え注意）

| | パス | 何をするか |
|---|---|---|
| ❌ 使わない | freee**会計** `POST /api/1/receipts` | **受け取った**証憑をファイルボックスに**アップロード**する |
| ✅ 使う | freee**請求書** `POST /receipts` | 領収書を**発行**する |

Web 検索や `freee-accounting-sdk-*` の `ReceiptsApi` は前者を指す。参考にしないこと。

## 1. freee でアプリを登録する

1. [freee アプリストア 開発者ページ](https://app.secure.freee.co.jp/developers/applications) を開く
2. 「新規アプリ作成」→ アプリ名を入力
3. **コールバックURL** に本番のコールバックを登録する

```
https://api.walover-co.work/api/integrations/freee/callback
```

4. **利用可能なスコープ**で、freee請求書の読み取り／書き込みを有効にする

> ⚠️ **スコープはアプリ登録画面で設定する。** freee の認可URLには `scope` パラメータを
> 渡さない仕様のため、コード側でスコープを変えることはできない。
> 領収書を発行できない場合は、まずここの設定を疑う。

5. 発行された **Client ID** と **Client Secret** を控える

## 2. Worker にシークレットを設定する

`.env` には書かない（`wrangler secret put` を使う）。

```bash
cd apps/worker
npx wrangler secret put FREEE_CLIENT_ID
npx wrangler secret put FREEE_CLIENT_SECRET
```

コールバックURLを既定値から変える場合のみ:

```bash
npx wrangler secret put FREEE_REDIRECT_URI
```

## 3. 認可する

**管理画面 → freee 連携 → 「+ freee と連携する」** をクリックする。

> ⚠️ **ブラウザで `/api/integrations/freee/auth` を直接開くことはできない**（401 になる）。
> このエンドポイントは認証必須にしてある。公開のままだと誰でも有効な `state` を発行でき、
> 第三者が自分の freee 事業所で認可を完走する足がかりになるため。

1. freee にログイン
2. **事業所を選ぶ**（`prompt=select_company` を付けているため選択画面が出る）
3. 「許可する」
4. 完了画面に **接続ID** が表示される

トークンは `freee_accounts` テーブルに保存される。

## 4. 接続を有効化する（新規接続のみ）

**管理画面 → freee 連携** の一覧で、対象の接続の「有効化」を押す。


> ⚠️ **新規の接続は「保留」（`is_active = 0`）で保存され、そのままでは使われない。**

`/callback` は freee からのブラウザリダイレクトを受けるため、**認証をかけられない公開
エンドポイント**になっている。つまり第三者が公開の認可URLを自分で踏み、**自分の freee
事業所**で認可を完走すると、その人のトークンがこの DB に入りうる。
自動で有効化してしまうと、領収書がその人の事業所に発行されてしまう。

そこで **新規接続は必ず保留で保存し、有効化は認証済みの管理画面から行う**。

- 一覧の**事業所名／事業所ID**を確認してから有効化する
- 身に覚えのない接続が並んでいたら**有効化せず削除する**
- 有効な接続は**常に1本**。別の接続を有効化すると、元の接続は自動で保留に戻る

> ℹ️ **事業所名はベストエフォートで取得する。** 認可時に freee会計の事業所一覧APIを
> 叩いて表示名を保存するが、アプリのスコープに会計APIが含まれない場合は取得できず
> 「（名称未取得）」と表示される。その場合は**事業所IDの数字で見分ける**。
>
> なお **`company_id` が取れなかった認可は保存せずエラーにする**。
> 見分けのつかない接続を作らないための意図的な仕様（手順3でエラーになった場合は下記参照）。

**再認可（90日ごと）の場合は保留にならない。** 同じ `company_id` の接続が既にあれば
トークンを上書き更新するだけで、`is_active` は触らないため、稼働中の連携は止まらない。

### state 署名で防げること・防げないこと

認可URLに載せる `state` は `FREEE_CLIENT_SECRET` を鍵にした署名付きで、コールバック時に
署名と有効期間（10分）を検証している。

| | |
|---|---|
| ✅ 防げる | 当サービスの認可導線を経ていない、偽造・改ざん・期限切れのコールバック |
| ❌ **防げない** | 第三者が**自分でこの公開の認可URLを踏んで**正規の `state` を取得し、自分の freee 事業所で認可を完走すること |

つまり **state だけでは第三者の登録を止められない**。実際に守っているのは
上記の「**保留にして、有効化を管理画面に限定する**」ほうである。
有効化するときに `company_id` を必ず確認すること。

## ⚠️ 最重要：リフレッシュトークンは「1回限り・90日」

Google Calendar 連携と**ここが決定的に違う**。

| | Google | freee |
|---|---|---|
| refresh_token の再利用 | 何度でも可 | **1回限り**（使うと新しい値が発行され、古い値は無効） |
| 有効期限 | 実質無期限 | **90日** |

つまり:

- **リフレッシュのたびに新しい `refresh_token` を保存し直す必要がある。**
  保存し忘れると次回のリフレッシュが失敗し、連携が死ぬ
- **90日間まったくリフレッシュしないと失効する。** 現金受領が3か月発生しないと切れる
- 同時に2回リフレッシュすると片方が無効化される

→ 再認証は手順3をもう一度実行するだけでよい。

出典: [freee 認可コードフロー](https://developer.freee.co.jp/reference/認可コード)

## トラブルシューティング

| 症状 | 原因 |
|---|---|
| 認可画面で「リダイレクトURIが一致しません」 | 手順1で登録したコールバックURLと `FREEE_REDIRECT_URI` の不一致 |
| 「リンクが無効か、時間切れです」 | `state` の期限切れ（10分）。手順3からやり直す |
| 「事業所IDが取得できなかった」 | 認可時に**事業所の選択画面が出たか**を確認する。出ずに素通りしている場合はアプリ登録のスコープ設定を見直す。連携は保存されていないので、そのまま手順3をやり直してよい |
| 認可画面に飛ばず 500 になる | `FREEE_CLIENT_ID` の設定漏れ。Workers Logs にその旨が出る |
| しばらく使っていたら領収書が出なくなった | リフレッシュに失敗すると接続が**自動で保留に戻る**（管理画面で「⏸ 保留」になる）。手順3から再連携する |
| 事業所名が「（名称未取得）」 | アプリのスコープに会計APIが含まれていない。事業所IDで見分ければ運用上は問題ない |
| コールバックで「エラー」画面 | トークン交換の失敗。詳細は Workers Logs の `[freee callback]` を見る。**同じリンクを開き直しても直らない**（認可コードは消費済み）ので手順3からやり直す |
| 連携したのに領収書が発行されない | 接続が**保留のまま**の可能性。手順4で有効化する |
| 領収書の発行だけ失敗する | アプリ登録のスコープ不足（手順1の4）。認可をやり直す |

> トークンと領収書URLは**ログに出していない**（`console.log` に出すと、
> ログ閲覧権限だけで領収書が開けてしまうため）。追跡は接続IDと booking_id で行う。

## 領収書の発行（#46）

現金受領ボタンを押すと、freee請求書 API で領収書が作られる。

### API 仕様の出典

公開の OAS3 スキーマが唯一の一次情報（リファレンスサイトはログインが要る）。

```
https://raw.githubusercontent.com/freee/freee-api-schema/master/iv/open-api-3/api-schema.yml
```

- ベース URL: `https://api.freee.co.jp/iv`
- 発行: `POST /receipts`

> ⚠️ freee**会計**の `POST /api/1/receipts` は「受け取った領収書の画像をアップロードする」
> 別の API。発行はできない。ベース URL（`/api/1` と `/iv`）で見分ける。

### 取引先（partner）の設定が必要

freee は領収書を**必ず取引先に紐づける**（レスポンスの `partner_id` が必須）。
参加者ごとに取引先を作るとマスタが人数分汚れるので、**固定の取引先を1件**用意し、
領収書の宛名だけ `partner_display_name` で上書きする。

1. freee で取引先を1件作る（名称「イベント参加者」）

   入力するのは**名前だけ**でよい。住所・敬称・「書類に使用する名称」は空欄のままにする
   （宛名と敬称は領収書ごとに API から送って上書きするため）。
   「適格請求書発行事業者」は**相手が適格請求書発行事業者か**を表す欄なので、
   参加者は個人＝チェックしない。
   「請求設定 → 外税/内税」も触らなくてよい（発行時に毎回「内税」を明示的に送る）。

2. **取引先ID を控える**

   ⚠️ freee請求書の取引先フォームには**「取引先コード」欄が無い**。ID を使う。
   保存後に取引先の詳細ページを開き、URL 末尾の数字が取引先ID。

   ```
   https://settings.secure.freee.co.jp/partners/123325147
                                                ~~~~~~~~~ ← これ
   ```

3. `apps/worker/wrangler.toml` の `[vars]` に書く
   （秘密情報ではないので `wrangler secret` は不要。Git に残して変更履歴を追えるようにする）

```toml
[vars]
FREEE_PARTNER_ID = "123325147"
# 取引先コードが使える場合はこちらでも可（両方あればIDを優先）
# FREEE_PARTNER_CODE = "EVENT"
```

⚠️ **未設定だと領収書が1枚も発行されない**。freee が 400「取引先を指定してください」を返す。
ただし現金の受領記録は成功するので、画面はエラーにならない。
管理画面の黄色い警告に freee の文言がそのまま出るので、そこで気づく。

### 宛名の決まり方

3段のフォールバックで決まる。全部空なら発行しない（空欄の領収書を出さないため）。

```
① 申込フォームの「領収書の宛名」（任意入力）
② 申込者名
③ LINE の表示名（友だち紐付けがある場合）
```

③ が要るのは、LIFF の `getProfile()` が失敗すると申込者名が空文字で保存されるため。
管理画面には表示名が出ているのに領収書だけ出ない、という食い違いを防ぐ。

### 領収書に載る内容

| 項目 | 値 |
|---|---|
| 宛名 | 申込フォームの「領収書の宛名」→ 未入力なら申込者名 |
| 敬称 | 法人・団体に見えれば「御中」、それ以外は「様」（自動判定） |
| 領収日 | 現金を受領した日（**JST の暦日**） |
| 金額 | `event_bookings.amount`（受領時に `events.price` から焼き込み済み）・**税込** |
| 但し書き | 「〈イベント名〉 参加費として」 |
| 消費税 | 10%（軽減税率対象外） |

### 二重発行の防止

freee を呼ぶ**前に** `receipt_issued_at` を立てて発行権を取り、取れた1本だけが発行する。
受付に端末が2台あって同時に「現金受領」を押しても、領収書は1枚しか出ない。

Worker が発行の途中で落ちると発行権が残るが、**5分で自動的に奪い返せる**ので、
その予約が永久に発行不能になることはない。

発行に失敗したとき、発行権を返すかどうかは**「freee に作られていないと断言できるか」**で決める。

| 失敗の種類 | 発行権 | 押し直したとき |
|---|---|---|
| トークンを取れない（freee を呼んでいない） | 返す | すぐ再試行できる |
| freee が 4xx で拒否（設定ミスなど） | 返す | すぐ再試行できる |
| タイムアウト・通信断・5xx（**結果が不明**） | 保持 | 5分間は freee を呼ばない |
| 2xx だが URL が取れない（**作られている**） | 保持 | 5分間は freee を呼ばない |

一律に返すと、タイムアウト後の押し直しで2枚目が出る。逆に一律に保持すると、
設定ミスを直しても5分待たされる。だから種類で分ける。

2xx だが URL が取れなかった場合は、**領収書ID をログに出す**
（`receipt_id=...`）。freee 側に存在する1枚を特定する唯一の手がかりになる。
領収書ID は個人情報ではないので出してよい（URL は出さない）。

> ⚠️ 残る穴: タイムアウトから5分経つと発行権が解放されるため、そのあと押すと
> 2枚目が出る可能性は残る。freee を検索して既存の領収書と突き合わせる仕組みは #48 で入れる。

### トークンが切れたとき

freee 側でアプリ連携を解除すると、**有効期限内のトークンでも 401** になる。
401 を受けたら一度だけ取り直して再試行し、それでも 401 なら
「freee との連携が切れています。管理画面から連携し直してください。」と案内する。

### ⚠️ 落とし穴: 内税/外税と源泉徴収の計算方法は揃える

freee は `tax_entry_method`（内税/外税）と `withholding_tax_entry_method`（源泉徴収の
計算方法）の**組み合わせを検証している**。食い違うと 400 で拒否される。

```
freee 400: withholding_tax_entry_method が[out:税別価格で計算]の場合、
           tax_entry_method は[out:税別表示（外税）]を指定してください。
```

イベント参加費で源泉徴収は発生しないので `withholding_tax_entry_method` の値自体に
意味は無いが、**必須項目**なので何か入れる必要がある。`tax_entry_method` と同じ値にする。

実装では `TAX_ENTRY_METHOD` という1つの定数から両方に渡している
（2つに分けると片方だけ変えられてしまうため）。本番で実際に踏んだ（2026-09-06）。

### 発行に失敗したときの挙動

**現金の受領記録は必ず残す**。現金は物理的に受け取っているため、
発行失敗で受領まで巻き戻すと「受け取ったのに記録が無い」状態になる。

- API は 200 を返し、`receiptIssued: false` と理由を添える
- 管理画面は黄色の警告で「受領は記録／領収書は未発行」と出す
- 再発行は #48 で扱う

### ⚠️ 未検証: `report_url` が参加者から開けるか

`POST /receipts` が返す URL のフィールドは `report_url` で、スキーマ上の説明は
**「帳票詳細ページのURL」**。freee にログインしないと開けない可能性がある。

OAS3 を確認した限り、URL 共有（`invoice.secure.freee.co.jp/ivex/dl/<UUID>` の形式）の
リンクを**返すフィールドも、発行する API も存在しない**（`/receipts` にあるのは
index / templates / show / create / update / cancel / uncancel のみ）。

→ 参加者へ LINE で送る #47 の前に、実際に1件発行して `report_url` を
   ログアウト状態のブラウザで開いて確かめること。開けなければ #47 の設計を変える必要がある。

## 領収書を参加者に送る（#47）

### なぜ共有リンクの作成だけ手動なのか

freee請求書 API には**領収書の送付・共有のエンドポイントが無い**（公式スペック全 42
エンドポイントを確認済み）。共有リンク（`https://invoice.secure.freee.co.jp/ivex/dl/<UUID>`）は
**freee の画面操作でしか生成できず、API から読むこともできない**
（共有した後に `GET /receipts/{id}` を叩いても `sending_status` は `unsent` のまま）。

Webhook も使えない。freee請求書には Webhook 機能自体が存在しない
（Webhook があるのは会計・人事労務・freeeサインのみ）。

### 運営者の手順

```
1. 「現金受領」を押す            → freee に領収書が自動でできる（#46）
2. 参加者行の「🧾 領収書を送る」を押す
3. 「① freee でこの領収書を開く」→ freee で「URL共有」してリンクをコピー
4. ② 入力欄に貼って「登録」      → 形式検証・重複検出・freee との照合が走る
5. ④「LINEで送る」               → 参加者に届く
```

一覧のヘッダーに「🧾 3/5 送信」と出るので、**貼り忘れた人が残っていれば分かる**。

### ⚠️ 取り違え対策（A さんのリンクを B さんに送る事故）

領収書には宛名と金額が載るため、取り違えは**個人情報の漏洩**。
しかも LINE の送信は取り消せない。4 層で守っている。

| 層 | 仕組み | 効果 |
|---|---|---|
| 1 | 同じリンクを2人に登録できない（DB の一意制約） | **防ぐ**（クリップボード持ち越し） |
| 4 | freee に問い合わせて領収書番号を照合 | **防ぐ**（1で漏れる全パターン） |
| 2 | 参加者に送るのは自前の `/receipt/<token>` | **止める**（無効化できる） |
| 3 | 1件ずつしか開かない・末尾8文字を表示 | **防ぐ**（見失わせない） |
| 3.5 | 本文に受信者自身の宛名を書く | **気づく**（本人が最初に） |

第4層は freee の**非公開エンドポイント**（`HEAD /api/ivex/dl/<uuid>/0`）の
`Content-Disposition` から領収書番号を読んでいる。freee 側の変更で壊れうるので、
**壊れたら「未照合」と明示して人の確認に委ねる**（黙って通さない）。

### 誤配に気づいたとき

1. 参加者行を開き、**開封状態を確認する**
   - 「未開封 — 無効化すれば止められます」→ まだ間に合う
   - 「⚠️ 参加者が開封済み（日時）」→ **内容は既に見られている**。無効化しても取り返せないので、
     相手に連絡して削除を依頼する
2. 「リンクを無効化」を押す。以降そのリンクは 410 になる
3. 無効化すると**送信済みの記録も消える**ので、一覧のカウンタが「未送信」に戻る
   （対応が必要な参加者として残る）
4. freee で共有リンクを**作り直して**貼り直す
   - 無効化した予約に貼り直すと、トークンが作り直されるので、
     誤って渡ったリンクは死んだままになる
   - 誤って登録してしまったリンクは、**正しい参加者に登録し直せる**
     （無効化時に URL を解放しているため）

⚠️ **一度開かれると止められない**（転送先 URL がブラウザ履歴に残るため）。
無効化が効くのは「まだ開かれていない誤配」に対してだけ。

### 未照合のリンクを送るとき

freee との照合が通らなかった場合（freee の障害・仕様変更・#46 以前の古いデータ）は、
「リンクを開いて、宛名が◯◯になっていることを確認しました」にチェックしないと送信できない。
**このチェックはサーバー側で検査している**ので、画面を経由しない送信でも迂回できない。

### 閲覧期限は 60 日

freee の既定値。貼付時に自動で記録し、LINE の本文にも
「◯月◯日を過ぎるとダウンロードできなくなります」と入れる。
参加者は確定申告の時期に過去のトークを遡ることが多いので、期限は明示する。

## 現金を受け取ったあとにキャンセルされたとき（#65）

### 参加者は自分で取り消せない

現金受領済み（`cash_received_at` あり）の予約は、LIFF から取り消そうとすると断られる。

```
キャンセルできませんでした
お支払い済みのため、こちらからは取り消せません。主催者までご連絡ください。
```

**現金の返金は対面でしかできない**ので、システムだけ先に進ませない。
進ませると「受け取ったはずなのに記録はキャンセル」になり、いくら返すか分からなくなる。

### ⚠️ 取り消しは owner のみ

不可逆な送金（Stripe 返金）と領収書リンクの無効化を伴うため、
`admin-cancel` は `requireRole('owner')` にしてある。
owner 以外には「申込を取り消す」ボタン自体を出さない
（出すと、現金を返した後で 403 になり、**現金も戻らず予約も残る**）。

現金受領（cash-received）はロールを絞っていない。受付の通常業務であり、
取り消しとは性質が違うため。

### 運営者の手順

1. 参加者から連絡を受ける
2. **現金を返す**（対面・振込など）
3. 管理画面の参加者行「申込を取り消す」を押す
   - 確認ダイアログに受領額が出る（例:「現金 ¥100 を受領済みです」）
4. 画面に「**やれなかったこと**」が出る
   - 「⚠️ Stripe の返金に失敗しました」→ Stripe の管理画面から手動で返金する
   - 「⚠️ 領収書の共有リンクを無効化できませんでした」→ 手動で無効化する
   - 「⚠️ 参加者への LINE 通知は届いていません」→ 別の手段で連絡する

   何も出なければ全部うまくいっている。**出たものは必ず手で片付ける**
5. 取り消すと**領収書の共有リンクは自動で無効化**される
   - 参加者がリンクを開くと 410 になる
   - 返金したのに領収書を持ち続ける状態を防ぐため
6. **freee 側の領収書は手動で取り消す**
   - 参加者行の「freee でこの領収書を開く」から取り消す
   - ⚠️ 自動化していない。freee の取消は後から戻せないため

### 取り消したあとの表示

バッジは「❌ キャンセル」になるが、**受領の事実は別の印で残る**。

```
❌ キャンセル  ⚠️ 要返金 ¥100
```

⚠️ この印は「**現金を受け取った記録があるのにキャンセルされている**」という事実だけを表す。
返金したかどうかは追跡していないので、印は消えない。
